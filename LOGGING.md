# Логирование

API, Telegram-бот и Web Push worker пишут по одному JSON-объекту на строку в stdout.
Формат одинаковый, независимые образы не зависят друг от друга на уровне импортов.
Локальные модули `observability.py` содержат небольшой общий по формату код.

| Поле | Назначение |
| --- | --- |
| `timestamp` | Время UTC в ISO 8601. |
| `level`, `service`, `logger`, `event` | Уровень, сервис и стабильный код события. |
| `request_id` | Связь запросов и операций; бот передаёт его backend через `X-Request-ID`. |
| `method`, `route`, `status_code`, `duration_ms` | HTTP-операция, шаблон маршрута, результат и длительность. |
| `job_id`, `event_id`, `slot_id`, `update_id` | Технические идентификаторы при наличии. |
| `operation`, `provider`, `outcome`, `attempt`, `count` | Внешняя операция или фоновая работа. |
| `error_type`, `error_code`, `stack` | Тип ошибки, безопасный код провайдера и места в коде. |
| `provider_request_id` | Идентификатор запроса OpenAI для обращения в поддержку. |

Для каждого HTTP-запроса API есть завершение с кодом ответа и временем, включая ошибки
проверки прав и входа. Ошибки 4xx записываются как WARNING, 5xx — ERROR.
Непредвиденная ошибка до начала ответа возвращает нейтральный JSON 500 и `X-Request-ID`.
При ошибке после начала потокового ответа заменить ответ уже нельзя; ошибка логируется.
В `X-Request-ID` принимается только строка из 32 шестнадцатеричных символов;
остальные значения заменяются новым идентификатором.

Бот логирует результат обновления, исходящие вызовы backend и Telegram, получение
соединения polling, повторные попытки и результат доставки каждого уведомления.
Ошибки, которые обработчик превращает в ответ пользователю, тоже регистрируются.
Web Push логирует результат каждой доставки, номер попытки и сбой провайдера.
OpenAI логирует успех, длительность, незавершённый ответ и ошибки провайдера.
Изменения подписок, ответы на назначения и удаление события имеют отдельные записи.

Чистые функции, например сборка клавиатуры и форматирование дат, не создают записей
на каждый вызов. Их ошибки видны через обработчик операции. Это сохраняет полезность журнала.

## Приватность

Не записываются тела запросов и ответов, заголовки авторизации, cookies, пароли,
токены, одноразовые ссылки, тексты сообщений, история помощника и push endpoints.
Маршруты API записываются шаблонами, без query string. Неизвестный маршрут обозначается
`<unmatched>`, чтобы произвольный путь тоже не попал в журнал.

Форматтер экспортирует только разрешённые поля. Текст исключения, аргументы записи,
SQL-параметры, локальные переменные и строки исходного кода не экспортируются.
Для диагностики остаются тип исключения, файл, функция и номер строки.
Подробные штатные HTTPX/httpcore/SQLAlchemy access-логи отключены, поскольку могут
содержать URL с токеном Telegram или реквизиты запроса. Это действует и при DEBUG.
Новые записи добавляй статическим кодом события и техническими полями; не клади
секреты в разрешённые поля вручную.

## Уровни и просмотр

`LOG_LEVEL=INFO` используется по умолчанию. Доступны DEBUG, INFO, WARNING, ERROR, CRITICAL.
На DEBUG дополнительно видны успешные health-check, пустые запросы polling и проверки очереди.

```sh
docker compose logs --no-log-prefix --no-color --tail=100 api bot push-worker
docker compose logs --no-log-prefix --no-color --follow api bot push-worker
```

Docker ограничивает журнал каждого из трёх сервисов: пять файлов по 10 МБ.
Это локальная ротация, а не долговременное хранение. PostgreSQL, Caddy и frontend
сохраняют свой собственный формат журналов.

## Подключение мониторинга

Сборщик может читать stdout контейнеров и разбирать JSON приложения внутри Docker
поля `log`. Для поиска полезны `service`, `level`, `event`, `status_code`; `request_id`
связывает ошибки и операции. Идентификаторы пользователей и заданий лучше хранить
как поля записи, а не как высококардинальные labels.

Возможные сигналы: HTTP 5xx, повторяющиеся `bot.polling_retry`,
`notification.worker_retry`, `push.worker_retry`, ошибки OpenAI и рост повторных доставок.
Проверяй также отсутствие логов и остановку контейнера: упавший процесс не может
сам сообщать о своей недоступности. Сам мониторинг и внешняя отправка логов пока не подключены.
